# P3-03 — Checkout con pago (MUST)

**Rama** `feat/P3-03-checkout-pago` · **PR** vie 27 · **Merge** sáb 28 · **Dueño** P3
Depende del contrato de pago (`agrodirecto-backend/docs/specs/contratos.md`) y de la decisión go/no-go de P1-03 (jue 26 noche). Debe funcionar con **ambos** modos.

## Objetivo
Un flujo de compra sin pedidos duplicados, con pago sandbox (si existe) o simulado rotulado.

## Contexto
`Checkout.tsx:438` crea el pedido y solo vacía el carrito al pagar (:456); si el comprador sale tras confirmar, al volver se crea otro `PENDIENTE_PAGO`. Pago simulado en `Checkout.tsx:173,560-565` y `Orders.tsx:191`. Pedidos en vivo vía STOMP (`useTiempoReal.ts`).

## Cambios
1. Antes de crear, buscar un pedido `PENDIENTE_PAGO` del mismo carrito/productor y reutilizarlo (o guardar el id del pedido en estado persistente del checkout).
2. Tras `POST /pedidos/{id}/pago`: si `urlCheckout` existe → redirigir; al volver (`#pedidos`) mostrar "Confirmando pago…" hasta que el estado cambie (tiempo real o polling cada 3 s, máx. 2 min).
3. Si `urlCheckout` es null y `estado=RETENIDO` (simulado) → comportamiento actual, con el texto "Pago simulado" visible solo en ese modo.
4. Pago fallido o abandonado: el pedido queda en "Mis pedidos" con botón "Pagar" (ya existe en `Orders.tsx:152`).
5. Revalidar stock del carrito guardado antes de cotizar (`utils/carrito.ts`).

## Criterios de aceptación
- Dado salir y volver al checkout → no se crea un segundo pedido pendiente.
- Dado `urlCheckout` → redirección y, al volver con webhook procesado, estado "Pagado/Retenido".
- Dado modo simulado → un clic y el pedido queda retenido, con aviso claro.
- Error de la API (`regla`) se muestra con `sugerencia(regla)`.

## Tests
`tests/unit/` para la lógica de reutilización de pedido pendiente (extraer a util testeable); E2E en P4-04.

## Fuera de alcance
Cambiar el método de pago tras crear el cobro, múltiples productores en un carrito.

## Verificar
`pnpm test && pnpm typecheck && pnpm lint`; manual de ambos modos contra backend local.
